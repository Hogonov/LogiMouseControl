# Правила проекта LogiMouseControl

- Не проводи тесты нажатий кнопок мыши и прокрутки колёс. Пользователь проверяет это самостоятельно.
- Не имитируй такие нажатия или прокрутку и не запускай назначенные кнопкам действия для проверки, в том числе через «Проверить действие».
- Сборка, статические проверки и модульные тесты без управления мышью и без запуска назначенных действий разрешены.

## Процесс разработки (SDD)

Подробно: `docs/specs/README.md`.

- Перед изменением кода прочитай `docs/specs/README.md`, затронутые разделы `docs/specs/architecture.md` (компоненты, потоки, «Неприкосновенные правила» INV-…) и термины в `docs/specs/ontology.md`. Для аппаратных функций — `docs/HARDWARE_VALIDATION.md`.
- Без спецификации: опечатки, комментарии, форматирование, правка документации без изменения правил и фактов.
- Краткая спецификация (`docs/specs/templates/spec-short.md`): локальное исправление в одном компоненте, не затрагивающее контракты и инварианты.
- Полная спецификация, план и отчёт (`templates/spec.md`, `plan.md`, `report.md`): новое или изменённое поведение, несколько компонентов, формат `preferences.v1`, команды HID++, захват и восстановление, жизненный цикл, разрешения, потоки выполнения, флаги запуска, сборка и подпись. Список областей — `docs/specs/README.md`, «Выбор пути».
- ADR (`templates/adr.md`) — только когда решение меняет границу модулей, инвариант, формат хранения, идентичность приложения или добавляет зависимость либо сервис. Не придумывай причины прошлых решений.
- До реализации запиши ожидаемое поведение и критерии приёмки. Если решение меняется по ходу, сначала обнови спецификацию и при необходимости ADR. Уточняй у пользователя только неоднозначности, существенно влияющие на поведение, совместимость или объём.
- Влияние на архитектуру: сверь изменение с разделами `architecture.md`. Если меняются компоненты, потоки, владение состоянием, жизненный цикл, хранение, подпись или инварианты, обнови `architecture.md` в том же изменении; новые термины — в `ontology.md`; состав targets, сервисов, инвариантов или документов — в `knowledge-graph.json`. Найденное расхождение документа с кодом запиши в «Расхождения».
- Проверки выбирай по таблице «Выбор проверок» в `docs/specs/README.md`. Для изменений только документации достаточно проверки ссылок, JSON и `git diff --check`; сборку ради текста не запускай. Для кода — `./scripts/test.sh` и отладочная сборка; `./scripts/setup-local-signing.sh` не запускай.
- В отчёте у каждого критерия: выполнено, не выполнено или не проверено с причиной. Аппаратные сценарии помечай «ждёт проверки пользователем» со ссылкой на M-… и `docs/HARDWARE_VALIDATION.md`. Успешная сборка не подтверждает работу мыши.
- Задача завершена, когда критерии были записаны до реализации, каждое требование прослежено до проверки и результата, автоматические проверки прошли, ручные переданы пользователю, непроверенное названо, документы обновлены, статус спецификации актуален.
