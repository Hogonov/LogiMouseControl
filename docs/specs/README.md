# Процесс разработки LogiMouseControl

Spec-Driven Development в этом проекте: ожидаемое поведение и критерии приёмки записываются до реализации, архитектура описывает фактический код, а результат проверяется по заранее определённым критериям. Главное — сохранить работающий функционал. Решение о процессе: [ADR-0001](adr/0001-sdd-process-and-structure.md).

## Этапы

```text
запрос → спецификация → технический план → задачи → реализация → проверка критериев → актуализация документации
```

| Этап | Вход | Результат | Условие завершения |
|---|---|---|---|
| 1. Запрос | Сообщение пользователя или найденная проблема | Выбран путь (без спецификации, краткий, полный), заведена папка `changes/NNNN-slug/` | Понятно, что меняется. Неоднозначности, которые существенно влияют на поведение, совместимость или объём, заданы пользователю; остальные записаны как допущения в спецификации |
| 2. Спецификация | Запрос; `architecture.md`, `ontology.md`, затронутый код | `spec.md` по шаблону: ожидаемое поведение, требования R-…, критерии AC-…, проверки V-… и M-… | У каждого R есть AC; у каждого AC есть проверка; перечислены затронутые инварианты; блокирующих открытых вопросов нет. Статус — «готово к реализации» |
| 3. Технический план | `spec.md` | `plan.md`: подход, альтернативы при необходимости, влияние на архитектуру, решение о ADR | Ответы на все вопросы таблицы «Влияние на архитектуру»; ADR создан, если нужен |
| 4. Задачи | `plan.md` | Таблица T-… в `plan.md`: порядок, связь с R-…, файлы и символы, проверки | Каждое R покрыто задачей; каждая задача проверяема по отдельности |
| 5. Реализация | Задачи, спецификация | Код и проверки; статус «в работе» | Код соответствует требованиям; автоматические проверки задачи проходят. Если решение меняется, сначала обновлены спецификация и при необходимости ADR |
| 6. Проверка критериев | AC-…, V-…, M-… | Результат каждого AC: выполнено, не выполнено или не проверено с причиной. Краткий путь — раздел «Результат» в `spec.md`, полный — `report.md` | Все автоматические AC выполнены; ручные M-… переданы пользователю и явно помечены «ждёт пользователя». Статус — «реализовано» |
| 7. Актуализация документации | Отчёт, diff | Обновлены документы из таблицы выше, которые затронуло изменение | Документы не противоречат коду в затронутой области. После ручной проверки пользователем статус — «подтверждено» |

Для краткого пути этапы 3 и 4 пропускаются: задача одна и описана в спецификации. Отдельных согласований каждого этапа не требуется: пользователь участвует, когда нужно решить неоднозначность или выполнить ручную проверку.

Статусы изменения: черновик → готово к реализации → в работе → реализовано → подтверждено. Также «отменено». «Реализовано» не означает, что функция работает на мыши.

## Выбор пути

| Путь | Когда | Документы |
|---|---|---|
| Без спецификации | Опечатки, комментарии, форматирование; правка документации, не меняющая правил и фактов | Только коммит |
| Краткий | Локальное исправление в одном компоненте с понятным ожидаемым поведением. Не меняет контракты и инварианты из списка ниже | `spec.md` по [краткому шаблону](templates/spec-short.md) |
| Полный | Новое или заметно изменённое поведение; изменение контракта; несколько компонентов; любое из списка ниже | `spec.md`, `plan.md`, `report.md`; ADR при необходимости |

Изменение идёт полным путём, если затрагивает хотя бы одно:

- формат `preferences.v1` (INV-14);
- команды HID++, захват, освобождение или восстановление контролов (INV-5, INV-6, INV-10…INV-13);
- жизненный цикл: пауза, сон, отключение, выход, помощник (INV-16);
- разрешения, обнаружение конфликтов (INV-7);
- потоки выполнения или владение состоянием (`architecture.md`, подраздел 5.1);
- флаги запуска, сборку, подпись, идентичность приложения (INV-15);
- приватность, сеть, зависимости (INV-3, INV-4).

Если по ходу краткого пути выясняется, что задета одна из этих областей, спецификация переводится на полный путь до продолжения реализации.

### Когда нужен ADR

ADR пишется, если решение меняет границу модулей, инвариант, формат хранения, идентичность приложения, добавляет зависимость или внешний сервис, либо выбирает между существенно разными подходами, которые будет дорого поменять. Обычное исправление и новая функция в существующих границах ADR не требуют. Причины прошлых решений записываются только по источникам; если причина неизвестна, в ADR пишется «не зафиксировано».

## Идентификаторы и прослеживаемость

| Префикс | Что | Где определяется | Область уникальности |
|---|---|---|---|
| `CH-NNNN` | Изменение | Имя папки `changes/NNNN-slug/` | Проект |
| `R-NN` | Требование | `spec.md` | Изменение |
| `AC-NN` | Критерий приёмки | `spec.md` | Изменение |
| `V-NN` | Автоматическая проверка | `spec.md` | Изменение |
| `M-NN` | Ручная проверка пользователем | `spec.md` | Изменение |
| `T-NN` | Задача | `plan.md` | Изменение |
| `INV-N` | Инвариант | `architecture.md` | Проект |
| `D-NN`, `U-NN`, `P-NN` | Расхождение, неизвестное, предложение | `architecture.md` | Проект |
| `ADR-NNNN` | Решение | `adr/NNNN-slug.md` | Проект |

Вне своего изменения идентификатор пишется полностью: `CH-0002/R-03`. Идентификаторы не переиспользуются и не перенумеровываются; отменённый пункт помечается «отменено».

Цепочка прослеживаемости:

```text
R-… (spec.md) → AC-… (spec.md) → T-… (plan.md) → V-… / M-… (spec.md) → результат (report.md или «Результат» в spec.md)
```

Каждый документ ссылается на соседние по идентификатору и не копирует их текст. Отчёт содержит только идентификаторы, результат и ссылки на коммиты.

## Выбор проверок

Агент не проверяет физические кнопки и прокрутку, не имитирует их и не запускает назначенные действия, включая «Проверить действие» (INV-1, INV-2).

| Что изменено | Проверки агента | Проверки пользователя |
|---|---|---|
| Только документация | Ссылки, валидность JSON (`python3 -m json.tool docs/specs/knowledge-graph.json`), `git diff --check`. Сборку не запускать | — |
| `Sources/MouseCore` | `./scripts/test.sh` с новой проверкой в `Tests/MouseCoreTests/MouseCoreTests.swift`, зарегистрированной в `Checks.main()`; `git diff --check` | Если меняется поведение на мыши |
| `SpotlightShortcut.swift` | `./scripts/test.sh` (проверки `Tests/SpotlightShortcutChecks`) | Вызов Spotlight |
| Прочий код приложения | `./scripts/test.sh`; отладочная сборка `swift build --disable-sandbox --scratch-path .build --product LogiMouseControl` с переменными кэша из `scripts/build.sh` (полная команда — `.claude/skills/verify/SKILL.md`) | По затронутым функциям |
| Views | Всё выше и `--render-artwork-preview .build/preview` из отладочной сборки, просмотр PNG. Приложение для проверки не запускать | Взаимодействие |
| HID, захват, жизненный цикл, прокрутка, действия | Всё выше и ревью агентом `hid-reviewer` (`/hid-review`) | Пункты `HARDWARE_VALIDATION.md` и M-… |
| Формат `preferences.v1` | Проверка в `MouseCoreChecks`, которая декодирует JSON прежнего формата | Настройки сохраняются после обновления |
| Сборка, подпись | `./scripts/build.sh` (перезаписывает `dist/`; нужен сертификат; `setup-local-signing.sh` не запускать) | Разрешения не запрашиваются повторно |

О непроверенном сообщается явно: в отчёте раздел «Не проверено» перечисляет сценарии, причину и кто проверит. Формулировки «работает» и «исправлено» для аппаратной функции без ручной проверки пользователем не используются: пишется «реализовано, ждёт проверки на мыши».

## Завершённая задача

Задача завершена, когда:

1. ожидаемое поведение и критерии приёмки были записаны до реализации и соответствуют сделанному;
2. каждое требование прослеживается до проверки и результата;
3. все автоматические проверки из спецификации выполнены и прошли;
4. ручные проверки перечислены для пользователя со ссылками на M-… и `HARDWARE_VALIDATION.md`;
5. непроверенные сценарии названы явно;
6. затронутые документы обновлены и не противоречат коду;
7. статус спецификации отражает фактическое состояние.
