# Архитектурная конституция LogiMouseControl

Версия: 1.0.0  
Дата: 2026-09-22  
Статус: действующая

## Назначение системы

LogiMouseControl — локальное нативное приложение для управления Logitech MX Master 4 по Bluetooth на macOS 14+. Приложение предоставляет настройку HID++-возможностей устройства, обработку прокрутки и дополнительных кнопок, профили приложений и локальное кольцо действий.

Система работает без аккаунтов, сетевого клиента, телеметрии и сторонних runtime-зависимостей. Аппаратные возможности считаются подтверждёнными только после отдельной проверки пользователем на физическом устройстве.

## Архитектурный стиль

Проект является модульным монолитом с двумя Swift Package Manager targets:

- `MouseCore` — платформенно-лёгкое ядро с протоколом HID++, моделями настроек, каталогом изображений и математикой прокрутки.
- `LogiMouseControl` — исполняемое macOS-приложение с UI, интеграциями AppKit/IOKit/CoreGraphics, координацией состояния и аппаратным доступом.

Внутри исполняемого target применяется слоистое разделение:

1. Представление: SwiftUI views и AppKit-панели.
2. Координация приложения: `AppModel` и точки входа из `AppEntry`.
3. Прикладные сервисы: `DeviceService`, `ScrollEngine`, `ActionExecutor`, `RingController`, `CaptureGuardian`.
4. Инфраструктура: `HIDTransport`, системные API macOS и `UserDefaults`.
5. Ядро: типы и чистая логика из `MouseCore`.

## Границы компонентов

### MouseCore

`MouseCore` не должен зависеть от SwiftUI, AppKit или IOKit. Здесь находятся сериализуемые настройки, HID++-пакеты, преобразование аппаратных значений, интегратор прокрутки и метаданные изображений устройства. Логику, которую можно проверить без macOS UI и физической мыши, следует по возможности размещать здесь.

### AppModel

`AppModel` — единый координатор пользовательского состояния. Он связывает разрешения macOS, снимок устройства, настройки, активный профиль и жизненный цикл сервисов. Views не должны напрямую управлять HID-транспортом или исполнять системные действия.

### DeviceService и HIDTransport

`DeviceService` владеет протоколом работы с возможностями устройства, последовательностью команд, подтверждением записей и восстановлением исходного состояния. Блокирующие HID-транзакции выполняются вне main thread и последовательно.

`HIDTransport` отвечает только за подключение к точному VID/PID `046D:B042`, кодирование запросов, строгую корреляцию ответов и доставку незапрошенных событий. Транспорт не захватывает всё устройство и не должен блокировать стандартный HID-ввод.

### Исполнение ввода и действий

`ScrollEngine` преобразует аппаратные смещения в маркированные CoreGraphics-события и прекращает инерцию при конфликтующем пользовательском вводе. `ActionExecutor` изолирует системные действия, сочетания клавиш, медиаклавиши и запуск приложений. `SpotlightShortcut` отдельно инкапсулирует работу с системным symbolic hotkey.

### Безопасное восстановление

Перед изменением diversion-состояния `CaptureGuardian` получает снимок восстановления через pipe. При аварийном завершении основного процесса дочерний процесс возвращает контролы в native HID. Снимок существует только в памяти и не сохраняется на диск.

## Неприкосновенные правила

1. Не выполнять автоматические проверки физических нажатий, прокрутки или назначенных действий. Такие проверки выполняет пользователь.
2. Автоматическая верификация может использовать сборку, статические проверки, чистую логику и подставные зависимости, которые не генерируют ввод и не запускают приложения.
3. Не сохранять серийный номер, Bluetooth-адрес, историю нажатий, перемещений или активных приложений.
4. Не добавлять сеть, телеметрию, аналитику, автообновление или облачную синхронизацию без отдельного архитектурного решения.
5. Аппаратная запись считается успешной только после ответа и проверки состояния устройства; при ошибке пользовательская настройка не сохраняется как применённая.
6. Перед diversion аппаратного контрола должен существовать актуальный recovery snapshot.
7. Все разрешения и конфликтующие драйверы проверяются до включения обработки.
8. Изменения должны сохранять совместимость с macOS 14+ и Swift tools 5.9, если отдельная спецификация не меняет эти границы.
9. Новые функции не должны изображаться работающими в UI до появления реальной реализации и проверяемого состояния.

## Данные и хранение

- Пользовательские настройки кодируются через `Codable` и хранятся в `UserDefaults` домена `local.alexandr.LogiMouseControl` под версионированным ключом `preferences.v1`.
- Профиль приложения идентифицируется bundle identifier и хранит только настройки, имя и локальную ссылку, необходимые для конфигурации.
- Изображения и их метаданные поставляются внутри `.app`; сеть для отображения устройства не используется.
- Временное состояние захвата и восстановления не должно становиться журналом действий.

## Конкурентность и жизненный цикл

- IOKit callbacks обслуживаются на main run loop.
- Блокирующие запросы устройства выполняются последовательной очередью `DeviceService`.
- Одновременно допускается один ожидающий HID++-запрос со строгим сопоставлением ответа.
- Сон, пробуждение, завершение сессии, отключение устройства и закрытие приложения должны останавливать прокрутку, закрывать кольцо и освобождать либо восстанавливать контролы.

## Проверки качества

Минимальная автоматическая проверка изменений:

- `./scripts/test.sh` для чистой логики `MouseCore` и изолированных проверок Spotlight;
- `./scripts/build.sh` для сборки и проверки подписи, если локальный signing identity доступен;
- `git diff --check` для контроля формата патча;
- ручная проверка на физической мыши только пользователем и только когда она действительно нужна.

## Изменение конституции

Архитектурное изменение должно обновлять этот документ, если оно меняет границы модулей, модель хранения, аппаратную безопасность, приватность, минимальную версию macOS или правила проверки. Термины предметной области синхронизируются с `docs/specs/ontology.md`.
